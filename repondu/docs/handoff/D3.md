# Handoff D3 — Boucle avis → réponse → veto → publication → log

## Fait
- `process_establishment` : pour chaque avis sans réponse ni brouillon, brouillon B1 (+ filtre
  B2), puis notification client (`notify_client`) : Telegram avec boutons Approuver / Veto si
  le client est lié, sinon mail de service tagué `[Répondu #id]` (« OK » pour approuver,
  « VETO » pour bloquer, « publié dans 24 h sauf veto ») ; SMS court en plus si mobile. Un
  brouillon `needs_human` n'est publié qu'avec un « OK » explicite. Tout est journalisé dans
  `client_messages`.
- Veto/approbation par mail : `poll_service_inbox` (boîte `SERVICE_IMAP_*`) → `process_client_reply`
  (tag dans l'objet, première ligne « ok/oui/d'accord » → approuvé, « veto/non/refus/stop » →
  refusé, idempotent par Message-ID, notification Telegram).
- Approbation automatique au délai : `auto_approve_due` (B3) dans le scheduler.
- Publication semi-manuelle : Telegram `/apublier` (texte à coller) puis `/publie <id>`, ou
  `GET /replies/to-publish` + `POST /replies/{id}/published` → `published_at`, l'avis passe
  `has_owner_response = 1` avec le texte (les métriques et rapports en tiennent compte).
- Mesure du DoD : `GET /stats.service` → `median_delay_h`, `pct_under_24h` (avis → publication),
  `pending_veto`, `to_publish`, clients actifs, statuts d'onboarding.
- Tests : boucle mail + SMS, Telegram avec boutons, vetos par mail (approuvé / refusé / doublon /
  inconnu / déjà décidé), publication + log + stats, cycle dû / forcé, boîtes du service.

## Points d'attention
- Le délai < 24 h dépend de l'humain qui colle la réponse : `/apublier` à chaque passage
  quotidien de 15 min (PRD §3). `pct_under_24h` dans `/stats` le mesure.
- `SERVICE_FROM_ADDRESS` doit être une boîte réelle relevée en IMAP (`SERVICE_IMAP_*`) pour que
  les « OK » / « VETO » par mail soient pris en compte.
